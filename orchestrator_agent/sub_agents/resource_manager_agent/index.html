    Resource Manager Agent

    The resource manager loop prepares every job with the Google Drive assets the downstream content agents expect. It replaces the legacy batch implementation with a deterministic iterator that claims two jobs at a time, runs a resilient pipeline worker for each, and keeps the orchestrator informed about overall progress.

    Ready For Resources
    v resource_database_iterator   (auth check, claim up to two jobs)
resource_manager_loop
    |--- resource_pipeline_worker_1  (process_job_resources)
    `--- resource_pipeline_worker_2  (process_job_resources)
Ready For Content

    By default the loop uses the deterministic pipeline workers so the Google APIs are called directly without accruing LLM context (no more 429 storms). Setting RESOURCE_FORCE_PIPELINE=false switches the two worker slots to the LLM-based resource_manager_1 and resource_manager_2 agents that share the same tool belt but can narrate their work for debugging sessions.

    Loop Anatomy

    1. resource_database_iterator

    • Gatekeeping: Verifies Google Drive prerequisites and, if credentials exist but no token is cached, triggers OAuth before claiming a job.
    • Atomic claims: Grabs up to two jobs with status Ready For Resources (one per worker slot) and writes them into session state as job_1 / job_2.
    • Progress tracking: Maintains total_processed, appends timestamps under resource_loop_progress, and emits iteration summaries.
    • Recovery: If the queue is empty but rows remain in_progress, calls release_stale_in_progress_jobs to free abandoned claims before retrying.
    • Shutdown: When no pending or in-flight work remains, raises an escalate event so the LoopAgent exits cleanly and records a completion summary in session state.

    2. Worker slots (resource_pipeline_worker_1 / _2)

    • Primary path: Deterministic ResourcePipelineWorker (a BaseAgent) reads its assigned job from session state and runs process_job_resources(job_id=...). That pipeline creates the Drive folder, copies the role-specific resume, exports PDFs, and writes database links in one transaction.
    • Fallback safeguards: After each run the worker clears its job slot and appends the job ID to completed_jobs for orchestrator metrics. Exceptions are logged but the job remains available for the next iteration.
    • Optional LLM workers: When RESOURCE_FORCE_PIPELINE=false, the loop swaps in resource_manager_1 and resource_manager_2 (LlmAgents) that follow RESOURCE_WORKER_PROMPT. Each worker still delegates to process_job_resources, with initiate_google_drive_auth exposed for first-run credential repair.

    3. Loop coordination

    • Callbacks: resource_loop_before_agent_callback and _after_agent_callback log iteration boundaries, update jobs_remaining, and expose queue counts to the orchestrator UI.
    • Safety limits: max_iterations is capped at 50 per invocation to avoid runaway loops; the iterator escalates as soon as the queue is empty so the orchestrator can re-enter later if new jobs arrive.
    • Junior agent: A lightweight junior_resource_manager_agent remains available for manual cleanup (uses cleanup_rejected_job_folders) but is no longer part of the main loop.

    Tools Used

    • check_google_drive_prereqs - confirm required Drive folders and credentials exist before a job is claimed.
    • trigger_google_auth / initiate_google_drive_auth - launch the OAuth flow when the shared token is missing or expired.
    • get_next_job_for_resources, release_resource_job, release_stale_in_progress_jobs, check_resource_queue_size - atomic job claim, release, and queue introspection helpers.
    • get_job_details, get_role_type_for_job - fetch context (title, role type, existing links) for logging and verification.
    • process_job_resources - end-to-end folder creation, resume copy, PDF export, and database updates used by every worker path.
    • create_company_folder, copy_google_drive_file, convert_google_doc_to_pdf, save_documents_to_drive, cleanup_rejected_job_folders - granular Drive operations leveraged inside the pipeline and by the junior agent.
    • complete_resource_processing - final status update once artifacts are written.
    • memorize, recall_all - memory tools only exposed on the junior agent for legacy clean-up workflows.

    Logging & Diagnostics

    • utils/resource_logging.py writes detailed, timestamped logs under logs/ with contextual emojis (claiming, waiting, completion) so you can trace the entire loop for a given run.
    • Iterator and worker callbacks record claimed job IDs, queue sizes, and fallback executions; look for RESOURCE_1/2 and PIPELINE prefixes when debugging.
    • Set CONTENT_CONSOLE_LEVEL=DEBUG (shared logging env) to mirror the loop feed in stdout while retaining full detail in the log files.

    Testing & Evaluations

    • Run the full suite: pytest -v orchestrator_agent/sub_agents/resource_manager_agent/tests.
    • test_resource_manager_integration.py drives the LoopAgent with in-memory fixtures to ensure jobs progress from Ready For Resources to Ready For Content via process_job_resources.
    • test_pipeline_link_extraction.py validates the Google Docs parsing utilities used during PDF/link propagation.
    • Batch regressions (test_batch_resource_manager_*) remain to protect against accidental reintroduction of the legacy batching edge cases.
    • run_tests.py offers a quick wrapper for local iteration inside the tests/ directory.

    Operational Notes

    • Ensure shared Google credentials live under orchestrator_agent/shared_libraries/; the iterator will refuse to claim jobs until check_google_drive_prereqs returns ok.
    • The loop automatically resets total_processed and clears job slots after a successful run so repeated invocations start fresh.
    • Jobs exit the loop with status Ready For Content and populated resume / PDF links so the content agent can immediately pick up the job what the content agent expects before generating bespoke materials.
